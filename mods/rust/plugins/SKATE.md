# ShortcutSkate server component

Development source for [#335](https://github.com/Dj-Shortcut/mw2-rust-skate-rewrite/issues/335) and [#337](https://github.com/Dj-Shortcut/mw2-rust-skate-rewrite/issues/337). This enables scoped movement acceptance; the client integrates the [shared components](../shared/README.md). The owner confirmed native compilation/loading of v0.2.0 and registration of all three Harmony patches, with source SHA-256 `078508fbdb67683f92d4943480250c7987bcbe051e60565713df06e41cbb465e`. Claude's [subsequent owner-session report](https://github.com/Dj-Shortcut/mw2-rust-skate-rewrite/issues/337#issuecomment-6098063930) records four minutes at up to 9.8 m/s, with one position correction. The owner later loaded v0.3.1 and [reported a rejected park placement](https://github.com/Dj-Shortcut/mw2-rust-skate-rewrite/issues/337#issuecomment-6106029865); no standing piece was confirmed. The v0.3.2 foundation-placement correction and v0.3.3 gesture addition below have not been installed or exercised on a live server by Codex. Practice behavior remains unverified.

Copy only `ShortcutSkate.cs` to `oxide/plugins/` on the owner's matching Oxide server when runtime validation is authorized. Eligible permitted players automatically arm after 1.5 seconds of continuous, supported, bounded movement; no console toggle is required. The warmup batches that stay within the bounds are accepted too (since 0.3.4): otherwise the game's own speed check refuses a rider who is faster than a walk during the warmup, its correction counts as a position discontinuity, and the warmup starts over without end. The server console says when skating is ready at load, and when a rider is accepted or loses acceptance (with the reason), at most every two seconds per rider. Rejected, stale or discontinuous movement disarms and resets that warmup. Death, sleep, disconnect, mount, wound, swimming, permission loss and unavailable patches revoke acceptance; a 0.1-second sweep covers lifecycle changes without a dedicated hook. Unload ends all sessions.

Player F1 commands `skate.toggle`, `skate.on`, `skate.off`, `skate.status` remain; a bind can use `bind k skate.toggle`. Movement commands affect only their caller. Explicit `on` requires dry support and current eligibility, and arms immediately. `off` or toggling an existing candidate opts out of automatic skating for that connection; successful `on` clears the opt-out. Status distinguishes waiting from active acceptance.

Default config:

```json
{"Version":1,"AllowEveryone":true,"MaximumHorizontalSpeed":14,"MaximumAirtime":1,"AutomaticEligiblePlayers":true,"AutomaticRearmSeconds":1.5,"ParkNextGesture":"I need wood","ParkCancelGesture":"Thumbs up","ParkPieceOrder":["halfpipe","bank","kicker","quarterpipe","ledge-low","ledge-high","long-ledge","funbox"]}
```

Existing Version 1 files may omit the automatic-rearm and park-gesture fields and receive these defaults. Set `AutomaticEligiblePlayers` false for manual activation. Rearm accepts 0.5–10 seconds. `AllowEveryone` grants effective access without changing saved Oxide permission grants; set false to require `shortcutskate.use`, then use `oxide.grant user <SteamID64> shortcutskate.use`. Speed accepts 1–50 m/s; airtime 0.1–2 seconds. Invalid/null/unknown config fields preserve the file and disable skating. Reload with `oxide.reload ShortcutSkate`.

## Session diagnostics

After a position correction, use player F1 `skate.status` and copy its complete output. It reports current readiness/mode/active state and unavailable reason, the configured limits, latest observation, last **active disarm**, last **successful activation**, and last lost warmup. These records include reason, age, validation interval, batch gap, horizontal path/allowance and derived speed, vertical path/allowance, support, candidate airtime/limit, accumulated duration/elapsed allowance, warmup/required duration, position discontinuity and batch/segment counts. Lifecycle/sweep stops include the last available batch's movement metrics; `last-batch-allowed` is the retained session flag, not proof of a present native hook call. Unknown or nonfinite observations are labeled `unknown`; they are not presented as zero speed or elapsed time. Numbers use invariant decimal points.

`HorizontalSpeed` means accumulated horizontal path exceeded speed×validation interval; `Airtime` includes the candidate unsupported interval before its reset; `BatchGap` means more than 0.5 seconds without an observation; `PositionDiscontinuity` means the cached path start differs from the previous end by more than 0.01 m. Other reasons distinguish invalid input, vertical/duration limits, eligibility/permissions, opt-out/lifecycle and patch exceptions. The first failing bound is retained, so the report identifies that refusal rather than asserting all other bounds were valid.

Counters are separate for active disarms, successful manual/automatic activations and interrupted warmups. Repeated inactive unsupported observations do not overwrite the last active disarm or count as fresh active disarms. Interrupted warmup is counted only when positive progress was lost. A successful automatic activation is recorded after both Begin and Observe accept the batch, before resetting warmup; repeating `skate.on` while already active is not another activation.

Players may query their own `skate.status <SteamID64>`. An administrator may query another explicitly named connected human player; authenticated RCON or the server console must supply that ID. Invalid/multiple arguments and unauthorized other-player requests are rejected before looking up a target. A playerless caller alone does not grant access. No arguments still mean the calling player's own status; a playerless caller receives usage instructions.

History is connection-local, kept across off/death/sleep/mount/wound, and cleared on disconnect, player-object replacement or unload. Storage is capped at 512 connections; when full, diagnostics report unavailable and movement acceptance continues with its existing rules. Counters saturate at long.MaxValue. Status formatting occurs only on request: there is no batch log/chat spam, disk history, permission grant or config migration.

This reports the plugin's decision, not the cause of every server correction. Support rays still conservatively charge unsupported intervals. A grind on an edge without walkable support can exceed the airtime bound; no grind exemption or bound relaxation is added. Native grind support and diagnostic console readability remain owner/client verification.

## Temporary practice area

In-game administrators can use `skate.practice.spawn` and `skate.practice.clear`. Spawn requests eight native stone floor tiles about twelve metres ahead: 15/30-degree ramps, a planar 12-degree bank, nominal 0.4/0.8-metre ledges and three adjoining tiles for a nominal nine-metre low ledge. Clear the existing area before another spawn. A dry, level, unoccupied area is required.
The candidate path is `assets/prefabs/building core/floor/floor.prefab`. No complete cached prefab inventory or asset bundle proves this path, dimensions, pivot or colliders; exact native heights remain unverified. Runtime preflight checks the manifest, prefab type and stone construction data before creation. Parts are tracked before spawning, marked unsaved and cleaned on failure, clear or unload. If an entity-kill hook refuses removal, the part remains tracked and cleanup reports failure; unload logs any outstanding count. Native placement, networking and cleanup still require owner validation.

## Persistent park pieces

Use the normal building plan to lay out individual park pieces. A connected, alive, awake, dry, unmounted administrator can select the next piece through the stock gesture wheel's **I need wood** gesture. The first selection is **halfpipe**, followed by bank, kicker, quarterpipe, ledge-low, ledge-high, long-ledge and funbox, then halfpipe again. English chat feedback names the selected piece and tells the admin to place a square foundation within 120 seconds. **Thumbs up** cancels it. Other players receive no park selection or park chat from their gestures.

`ParkNextGesture` and `ParkCancelGesture` configure the two gesture names. They must be distinct nonempty names of at most 128 characters, without surrounding whitespace or control characters. Resolution uses the native catalog's English label, translation token, convar name or gesture command, case-insensitively. A missing or ambiguous name, or two names resolving to the same native gesture, disables the gesture trigger and reports the reason in status; IDs are not guessed. `ParkPieceOrder` configures one to eight distinct names from the table below. Selection starts with that order's first piece, then cycles through it. A new selection renews the 120-second window; cancellation, expiry or successful placement makes the next gesture start at the first piece.

The existing F1 selection remains available:

```text
skate.piece bank
```

Then place one normal horizontal **square foundation** with the building plan (`assets/prefabs/building core/foundation/foundation.prefab`). It can be placed on the ground. The game validates and snaps it; its position and yaw anchor the assembly. The foundation remains an ordinary, unmodified block, and all park members are created above its actual construction bounds. It is separate from the saved park group and remains after group demolition.

Selection lasts 120 seconds. Successful park registration consumes it; unsuitable blocks and failed attempts retain it until the original expiry, cancellation or replacement. Placing an ordinary square floor does not trigger a park piece. A failure names the missing save identity field, capacity, native prefab, construction material, deployment data or bounds constraint, including the affected prefab/material. Retry with another foundation after addressing that cause. `skate.piece cancel` cancels selection. These are console commands, not chat commands.

`skate.status` includes the queried player's pending piece and seconds remaining, plus the availability of the gesture trigger. Its existing caller/explicit-admin-target access policy still applies.

The inspected cached Oxide 2.0.7815 and official 2.0.7820 assemblies do not emit a gesture-start hook. Their ownership-query hook runs before acceptance and can also run while building the wheel, so it cannot safely select a piece. v0.3.3 bridges only the accepted native start to the plugin's `OnPlayerGestureStarted` handler with its own Harmony patch. It inserts a void callback immediately after the unique accepted gesture assignment, preserves the original instructions and catches callback exceptions. A supported existing native hook needs no bridge; an unrecognized or ambiguous instruction shape disables the gesture trigger. Unload removes only this plugin's bridge. Ordinary F1 selection does not require that bridge.

`skate.piece halfpipe` selects the complete halfpipe as one saved group. The placed foundation anchors the first central floor tile; four authored tiles form a 6 × 6 m flat. Two lanes of opposing 15/35-degree transitions lead to elevated decks, producing a nominal 6 × 22.71 m ride area with decks at 2.50 m above the flat. The owner clarified that the two-by-two foundation footprint refers to that middle, with transitions and decks alongside it. One placed foundation triggers the whole assembly; additional foundations are not authored park members.

The flat uses native Stone floors; transitions/decks use native Metal floors, with Wood low walls behind the decks and upright stepped Metal half-wall side panels. The halfpipe has 36 native parts: sixteen ride floors, four wooden back rails and sixteen stepped metal side panels. Walls extend beyond the ride-area edges; side panels are set 0.35 m outside them. These are the game's existing building materials and prefabs; the tilted transitions and stepped sides approximate the reference picture. Curved sheet metal, custom rivets and graffiti textures are not added. Full native prefab dimensions, seams, collision and appearance need owner/Claude verification.

The quarterpipe is a faceted approximation. Dimensions assume nominal three-metre square floors and exclude collider thickness; native dimensions, seams and rideability need verification. Ledges expose ordinary floor edges; there is no custom round rail or client change. The assembly preserves the game's anchor rather than rounding it to a separate world-origin grid.

Creation checks native construction data, building privilege across the footprint, construction hooks, terrain/water and occupied space before spawning the assembly. Additional hook queries describe authored terrain-style world poses; they do not fabricate building sockets or reproduce the original snapped target. The ordinary building plan charges for its foundation; park blocks and their initial material grades are provided by this admin command. The first seven pieces start as Stone; the halfpipe uses the materials above. Parts retain the placing player's ownership and ordinary native health, damage, upgrading and decay. Individual hammer rotation is refused to preserve assembly geometry; demolish the assembly and rebuild at a new heading instead.

Use the normal hammer's demolish action on any park member to remove the assembly, subject to native demolition permission checks. The ordinary foundation is separate. A kill hook may refuse a member's removal; remaining members stay tracked and the command reports incomplete removal. Damage can leave a partial assembly. In-game admin F1, authenticated admin RCON or the actual server console can use `skate.pieces` with no arguments to list per-kind totals and placing owners' Steam IDs, including partial groups. Storage allows at most 256 groups and 128 pending selections, with a one-MiB metadata limit. Large assemblies can reach that file-size limit before the group-count cap; rejected additions retain the original foundation and pending selection.

Pieces are saved native building entities. Group metadata lives in `oxide/data/ShortcutSkate.Parks.json`; keep it with the matching world save. Owner and member IDs are stored as canonical decimal strings to retain the full unsigned 64-bit range. Strict manifest validation matches the wipe/save generation and each member's ID, prefab, owner and pose before restoring its grounded state or treating it as a group. Malformed metadata disables park creation/group control and preserves the file for diagnosis. Metadata from a different wipe/save generation is not adopted; a fresh manifest never recreates old blocks. Members with mismatched IDs, prefabs, owners or poses are removed from grouping. Save creation time is compared at the whole-second precision used by the native save header.

Placement re-reads the current native identity instead of rejecting a stale cached comparison. Wipe ID, save creation time, seed and size identify the generation. A checksum-only change revalidates existing members and updates the manifest for that same generation; it does not discard verified groups. A generation change starts new grouping without adopting old IDs and names the changed fields. Unavailable identity fields and a manifest write/readback failure produce explicit errors. A storage failure disables new placement until reload; it is not treated as checksum drift. Existing Version 1 member layouts remain compatible. Plugin unload preserves saved park blocks; `skate.practice.clear` only removes the separately tracked, unsaved practice area.

Skating readiness and movement-patch/config failures do not replace the park manifest's own readiness checks. The anchor is a normally validated foundation placement; authored tilted members are not proven equivalent to every native socket/placement rule. Real placement, reloading, restart, decay/upgrading and whole-piece hammer demolition remain owner validation. Codex ran no commands against a live server and made no Rust-client or Shadow PC run for v0.3.2. The owner installs and tests it; compilation does not establish that a piece stands.

## Movement boundary and verified server contract

The [current violation hook](https://docs.oxidemod.com/hooks/player/OnPlayerViolation) is `object OnPlayerViolation(BasePlayer, AntiHackType, float, GameObject)`. Any non-null return skips `AntiHack.AddViolation`. `SpeedHack` and `FlyHack` are the enum names (values 2 and 3).
Offline IL inspection of genuine cached Oxide 2.0.7815 and official 2.0.7820 (9 October 2026) proves that `ValidateMoves` separately consumes the completed speed/fly result arrays and selects movement rejection. Cancelling only the violation hook does **not** cancel those reject paths. The public pause methods provide larger finite forgiveness; they do **not** disable the tests.

This plugin uses Oxide's `Oxide.Core.Plugins.AutoPatchAttribute` with Harmony 2.3.1.1. A prefix on `AntiHack.ValidateMoves(in BasePlayer.PlayerServerStates.ReadOnly, NativeArray<int>.ReadOnly, NativeArray<BasePlayer.PositionChange>)` computes one decision per player/batch. Postfixes on `AreSpeeding(in ReadOnly, NativeArray<AntiHack.PlayerSpeedhackState>, NativeArray<int>.ReadOnly, NativeArray<bool>)` and `AreFlying(in ReadOnly, NativeArray<AntiHack.PlayerState>.ReadOnly, NativeArray<AntiHack.PlayerFlyhackState>, NativeArray<int>.ReadOnly, NativeArray<bool>)` clear only that eligible player's speed/fly result. The original checks run first; unrelated results and global convars are untouched. The finalizer closes the batch scope. Missing installed patches disable skating.

Every cached path segment contributes its horizontal length, preventing an out-and-back move from hiding behind its endpoint. The bound is horizontal path length divided by the **server validation interval**, not instantaneous per-packet speed: the cache has no segment timestamps. Intervals over 0.5 seconds, stale/corrected positions, nonfinite input, cumulative time inflation, horizontal excess or vertical path over 40 m/s end skating and receive no exemption.
Physical downward rays sample start, endpoints and interiors at spacing at most 0.1 m on Terrain/World/Construction/Deployed layers, ignore triggers and require a walkable normal. Client `modelState.onground` is never used. Any unsupported sample charges the whole interval as airtime. A fully supported batch resets airtime only after the previous airborne interval passes its limit. This deliberately conservative estimate can end skating on poor support or delayed packets.

`Shortcut.RustMod.SkateSessionBounds` retains `Begin(now,supported)`, `Observe(now,dt,horizontalPath,verticalPath,fullySupported,maxSpeed,maxAir)`, `End()`, `Active`, `AirSeconds` and pure `Eligible(...)`. `SkateSessionRearm` adds `Seconds`, `Reset()` and `Observe(now,dt,horizontalPath,verticalPath,supported,maxSpeed,requiredSeconds)`; progress requires monotonic bounded time and physically supported batches. `SkatePracticeLayout.TryPart(index,out SkatePracticePart)` supplies the eight finite layout positions. These helpers expose no engine/server types.

Bounds/Rearm also expose value-type `LastObservation`, retained across End/Reset. `SkateSessionHistory` stores copied observations and saturating enum-indexed counts; `SkateDiagnosticsStore` binds histories to a user ID and object identity. `SkateStatusAccess.TrySelectTarget` validates the explicit-target policy before native lookup; `SkateStatusReport.Format` produces the on-demand English report. These diagnostics do not change Observe outcomes or thresholds.

`SkateParkLayout` exposes `TryKind`, `Name`, `PartCount`, `TryPart` and `TryTransform`. `SkateParkPart` holds scalar local right/forward/height/pitch/yaw, its native prefab path and initial `SkateParkMaterial` (Stone, Metal or Wood); `SkateParkTransform` holds scalar world X/Y/Z/yaw/pitch. Transform rotates/translates offsets using the supplied anchor heading and adds the part’s local yaw for orientation; it normalizes yaw and rejects invalid inputs atomically. It neither queries terrain nor performs native building snapping.
