For each native movement batch, the plugin checks the complete finite path and tick duration in (0,0.5] seconds, then grants eligible permitted players up to their saved `MaximumHorizontalSpeed`. It sums XZ distance across every segment, including out-and-back travel. Ground support, airtime, warm-up, prior corrections and diagnostic timing do not withdraw a measured horizontal in-cap grant. Coordinates require finite values within +/-100000. Both result filters require current patch readiness, matching batch/player/cache identity, a measured horizontal grant, eligibility, general permission and no connection opt-out. Fly suppression additionally requires current server-admin status or server-granted `shortcutskate.fly`, and full absolute Y travel no greater than `200 * dt`. Invalid/incomplete batches retain native checking. Noclip and every other native result remain unchanged; no global convar is changed.

The server cannot attest that the separate client board is active. `shortcutskate.fly` is a trusted movement privilege, not board or ballistic proof: it also applies on foot and permits bounded hovering/climbing. `AllowEveryone` and `shortcutskate.use` do not grant it. In the authenticated administrator/server game console, `oxide.grant user <SteamID64> shortcutskate.fly` grants it and `oxide.revoke user <SteamID64> shortcutskate.fly` removes it. General permission is still required when `AllowEveryone` is false. Grant fly privilege only to players trusted with that custom movement; ordinary untrusted flight retains native checking.

The 200 m/s limit is a conservative source budget, not a measured native threshold. The current client caps falling at 30 m/s, permits steep tangent launches above 40 m/s and limits lip-assist velocity to 150 m/s. Trusted motion uses each fresh batch without a two-second airborne cutoff or ground-slope gate. Full absolute Y is measured before diagnostics; zero net height cannot hide an excessive up-and-down path. Actual native cache timing and movement acceptance remain unverified.

Player F1 commands `skate.toggle`, `skate.on`, `skate.off`, `skate.status` remain; a bind can use `bind k skate.toggle`. They affect only their caller. `on` requires eligibility/general permission, clears opt-out and enables the next measured batch; it grants no fly authority. Dry support is needed only to start ground diagnostics. `off` or toggling an existing candidate opts out for that connection. Permitted eligible players receive the horizontal policy without an activation wait, including with automatic diagnostics disabled. Status separately reports current fly authorization, the 200 m/s limit and last measured vertical path.

## Startup stall correction

For [#452](https://github.com/Dj-Shortcut/mw2-rust-skate-rewrite/issues/452), source 0.3.17 patches only the supplied `wasStalled` argument at `BasePlayer.UpdatePositionFromTick`. A five-second window starts on connection, successful waking or respawn, and is never renewed by ticks, commands or corrections. The plugin must be ready; the current player must be eligible, permitted, not opted out, and match the native player/cache identity, parent and unmounted model states. Snapshot/transfer ticks retain native handling. Death, sleep, disconnect and unload clear the window; at most 512 windows are retained. Reloading does not grant existing players a new window.

The complete buffered horizontal path plus the incoming segment must stay within the configured speed cap times the native validation interval, conservatively capped at 0.5 seconds. Nonfinite/nonpositive intervals, invalid coordinates and insufficient buffer capacity refuse the exemption. The cap is necessary because native stall returns can leave an unfinalized interval accumulating. The original interval, tick-distance check, cache enqueue, noclip and tick-buffer validation still run normally. Native stall getters/state and convars are unchanged. Ticks within 0.5 metres also need this bounded exemption because the stall branch otherwise returns without queuing them.

`skate.status` reports connection-local `Native stall would-correct` and `exempted` counters. Whenever an otherwise qualifying skater reaches the native stall decision with a supplied true stall flag and an endpoint distance over 0.5 metres, both exempted and retained corrections are counted. Anonymous server log lines report cumulative totals, the current decision/reason, startup age, distance, horizontal path and capped interval, at most once per two seconds across all players. Counters saturate; connection counters follow the bounded diagnostic store and clear on disconnect/replacement/unload. The log contains no player identifier. These are counterfactual stall decisions, not proof of a client correction or final native movement acceptance. Build and existing approved scenarios are offline verification; Harmony execution, native compatibility and join/wake/respawn gameplay still require a separately authorized live test.

## Optional support for ordinary building

`GroundedBuilding` defaults to `false`. In v0.3.5, setting it to `true` records newly placed, saving `StabilityEntity` objects and marks them grounded after normal placement bookkeeping. The builder must be connected, human, alive, awake, unwounded, dry, unmounted and unparented, with `shortcutskate.use` or `AllowEveryone`. An active skate session is not required; ride opt-out and movement-patch readiness do not deny this building option. Existing world objects are not retroactively adopted, and ordinary entities without stability support are unaffected.

Normal placement permission, collision and resource checks still happen first. Grounding does not grant ownership or change saving, health, damage, native upkeep/decay or demolition permission. A qualifying square foundation used as a park trigger can also receive this separate grounding record; park-group demolition still leaves the trigger foundation. Registration waits until the next tick because the game may parent the object after the placement hook. Missing identity, an unsaved parent, exceeded capacity or a metadata write/readback failure refuses new grounding. This cannot rescue an object already destroyed before registration; native placement and collapse behavior remain unverified.

Keep `oxide/data/ShortcutSkate.Grounded.json` with the matching world save. It is independent of the park manifest and stores at most 4096 members within one MiB. Records match the save generation, entity ID, prefab, actual owner, parent ID/prefab/owner/bone and **local** position/rotation. Owner and parent IDs use canonical decimal strings. Trusted live references refresh their local poses before save/unload, allowing normal rotation and parent movement without adopting an object whose ownership or parent identity changed. A refused kill leaves its record intact; confirmed destruction removes it. A checksum-only change revalidates members before updating metadata; another wipe/save generation never adopts old IDs.

With the option enabled and the plugin present during world loading, matching saved records restore `grounded` before normal spawning/loading. Corrupt metadata is preserved and refuses registration; a storage failure requires reload. `skate.status` includes `grounded-building`, `grounded-ready` and `grounded-records`; these are plugin state, not proof of a successful restart. Turning the option off or unloading does not unground live objects. It stops new registration, and disabling it stops restoration on a subsequent world load; unsupported structures may then collapse. Native restart/restoration has not been exercised by Codex.

For a server-wide alternative, the operator can use `server.stability false` in the authenticated server console. To request it on startup, add the same line, without a `+` prefix, to `server/<server.identity>/cfg/server.cfg` as described in the [Facepunch server guide](https://wiki.facepunch.com/rust/creating-a-server). This changes the server's general stability policy; the plugin option records only qualifying new placements. Decay is separate, and neither choice promises invulnerability or support for every construction type.

## Movement boundary and verified server contract

The [current violation hook](https://docs.oxidemod.com/hooks/player/OnPlayerViolation) is `object OnPlayerViolation(BasePlayer, AntiHackType, float, GameObject)`. Any non-null return skips `AntiHack.AddViolation`. `SpeedHack` and `FlyHack` are the enum names (values 2 and 3).
Offline IL inspection of genuine cached Oxide 2.0.7815 and official 2.0.7820 (9 October 2026) proves that `ValidateMoves` separately consumes the completed speed/fly result arrays and selects movement rejection. Cancelling only the violation hook does **not** cancel those reject paths. The public pause methods provide larger finite forgiveness; they do **not** disable the tests.

This plugin uses Oxide's `Oxide.Core.Plugins.AutoPatchAttribute` with Harmony 2.3.1.1. A prefix on `AntiHack.ValidateMoves(in BasePlayer.PlayerServerStates.ReadOnly, NativeArray<int>.ReadOnly, NativeArray<BasePlayer.PositionChange>)` computes one decision per player/batch. Postfixes on `AreSpeeding(in ReadOnly, NativeArray<AntiHack.PlayerSpeedhackState>, NativeArray<int>.ReadOnly, NativeArray<bool>)` and `AreFlying(in ReadOnly, NativeArray<AntiHack.PlayerState>.ReadOnly, NativeArray<AntiHack.PlayerFlyhackState>, NativeArray<int>.ReadOnly, NativeArray<bool>)` clear only that eligible player's speed/fly result. The original checks run first; unrelated results and global convars are untouched. The finalizer closes the batch scope. Missing installed patches disable skating.

Every cached path segment contributes its horizontal length, preventing an out-and-back move from hiding behind its endpoint. The bound is horizontal path length divided by the **server validation interval**, not instantaneous per-packet speed: the cache has no segment timestamps. Intervals outside (0,0.5], invalid counts/coordinates and horizontal excess receive no grant. Prior corrected positions, vertical speed, timing history and cumulative diagnostic duration do not gate the fully measured horizontal in-cap grant. The separate fly filter additionally requires fresh trusted authority and the full 200 m/s vertical-path budget. A failed diagnostic operation cannot revoke that completed grant; failures before measurement completion retain native results. Matching current scope/identity and authority are checked again when filtering.

The additive engine-free `SkateMovementPolicy` exposes `ValidTickCount`, `TryAccumulate(SkateMovementPoint from,to,horizontal,vertical,out nextHorizontal,out nextVertical)`, `TryAllow(dt,horizontal,maximumSpeed,out allowed,out reason)` and `CanFilter(ready,validating,matchingBatch,matchingIdentity,movementAllowed,eligible,permitted,optedOut)`. Failed accumulation retains prior path outputs. Invalid scalar requests return false/allowed=false with an ordered reason; valid overspeed returns true/allowed=false/HorizontalSpeed. Success grants no historical permission to another batch. `CanExemptFly(trusted,dt,vertical)` requires trusted authority, valid delta and a finite nonnegative full vertical path within `MaximumFlyVerticalSpeed * dt`; the native fly filter combines it with every fresh `CanFilter` guard. The public limit is 200 m/s.

Physical downward rays still sample start, endpoints and interiors at spacing at most 0.1 m on Terrain/World/Construction/Deployed layers for diagnostics, ignoring triggers and requiring a walkable normal. Client `modelState.onground` is never used. Support sampling is skipped when the measured vertical path already exceeds the diagnostic 40 m/s limit, bounding unnecessary work. Unsupported intervals/late landings can reset diagnostic bounds/rearm, with full path numbers retained. Those observations do not decide movement filtering.

`Shortcut.RustMod.SkateSessionBounds` retains `Begin(now,supported)`, `Observe(now,dt,horizontalPath,verticalPath,fullySupported,maxSpeed,maxAir)`, `End()`, `Active`, `AirSeconds` and pure `Eligible(...)`. `SkateSessionRearm` adds `Seconds`, `Reset()` and `Observe(now,dt,horizontalPath,verticalPath,supported,maxSpeed,requiredSeconds)`; progress requires monotonic bounded time and physically supported batches. `SkatePracticeLayout.TryPart(index,out SkatePracticePart)` supplies the eight finite layout positions. These helpers expose no engine/server types.

Bounds/Rearm also expose value-type `LastObservation`, retained across End/Reset. `SkateSessionHistory` stores copied observations and saturating enum-indexed counts; `SkateDiagnosticsStore` binds histories to a user ID and object identity. `SkateStatusAccess.TrySelectTarget` validates the explicit-target policy before native lookup; `SkateStatusReport.Format` produces the on-demand English report. These diagnostics do not change Observe outcomes or thresholds.

`SkateParkLayout` exposes `TryKind`, `Name`, `PartCount`, `TryPart` and `TryTransform`. `SkateParkPart` holds scalar local right/forward/height/pitch/yaw, its native prefab path and initial `SkateParkMaterial` (Stone, Metal or Wood); `SkateParkTransform` holds scalar world X/Y/Z/yaw/pitch. Transform rotates/translates offsets using the supplied anchor heading and adds the part’s local yaw for orientation; it normalizes yaw and rejects invalid inputs atomically. It neither queries terrain nor performs native building snapping.
